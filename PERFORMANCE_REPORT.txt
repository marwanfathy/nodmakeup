================================================================================
  1. EXECUTIVE SUMMARY
================================================================================

  The single most important finding is not a missing optimisation. It is a
  one-line bug in the root layout's cart provider that made the entire
  storefront render an EMPTY <body> on the server.

      // main-website/app/contexts/CartContext.tsx:74
      if (!isHydrated) return null;

  `isHydrated` was initialised to false and only ever set inside a
  useEffect. Effects do not run on the server, so the provider returned
  null during every server render. Because it wraps <Nav />,
  <main>{children}</main> and <Footer /> in the root layout, the whole body
  of every route was empty.

  Consequence: the storefront was a client-rendered application wearing a
  server-rendered costume. The HTML contained no content, so first paint
  always waited for JS download -> parse -> hydrate -> API round trip.
  No amount of image optimisation, font tuning or server-side caching could
  improve that, because there was no markup to improve.

  Headline before/after, measured on the production build:

      Route                     HTML bytes   Visible body text
      ---------------------------------------------------------------
      /en  (home)               15,550  ->  36,679      0  ->  499 chars
      /en/product/<slug>        25,848  ->  31,076      0  ->  691 chars
      /en/AboutUs               (empty)  ->  22,264      0  -> 1,024 chars
      /en/privacy-policy        (empty)  ->  24,581      0  -> 1,267 chars
      /en/shop                  (empty)  ->  26,768      0  ->  361 chars
      /en/bestsellers           (empty)  ->  21,008      0  ->  308 chars

  The "after" byte counts are exact and stable: three consecutive requests per
  route returned byte-identical responses, confirming the Data Cache is serving
  a fixed page rather than re-rendering per request.

  Two further real defects surfaced while isolating the above, both of which
  had been hidden by it:

      - useSearchParams() in the two analytics trackers marked every route
        BAILOUT_TO_CLIENT_SIDE_RENDERING.
      - /checkout could not be built at all; the build error was being
        masked by the blanket bailout.

  Everything in sections 3-6 was measured after those fixes.

================================================================================
  2. THE DOMINANT DEFECT — FULL DETAIL
================================================================================

  2.1 How it was found
  -------------------
  The initial audit recorded "homepage SSR HTML is <div hidden>" and treated
  it as an accepted property of a client-rendered storefront. That reading was
  wrong. The symptom was isolated by bisection on a production build, one
  variable per build:

      Experiment                                    Result
      ------------------------------------------------------------------
      Remove PageTracker + BehaviorTracker          still empty
      Remove await cookies() from root layout       still empty
      Remove Nav + Footer                           still empty
      Reduce body to bare <main>{children}</main>   RENDERED (404 page)
      Stub out useSearchParams()                    bailout marker gone,
                                                       DOM still empty

  The bisect showed the cause was in the two context providers wrapping the
  body, and reading CartContext.tsx located it on line 74.

  2.2 Why the guard existed, and why it was not needed
  --------------------------------------------------
  The guard is the standard "don't render until mounted" guard, normally used
  to avoid a hydration mismatch. Here it was protecting nothing:

      - the cart state starts as null and stays null until its own effect
        resolves it, so `itemCount` computes to 0 on the server AND on the
        first client render. The markup matches; hydration is clean.
      - nothing reads localStorage during render. `sessionHeaders()` in
        lib/api.ts guards on `typeof window === 'undefined'`, and
        `syncSessionId` is only called from effects and event handlers.
      - `isHydrated` was consumed by nothing else in the codebase. It was
        write-only state whose only effect was to blank the site.

  The guard was removed along with the now-dead state and its setter. The
  reasoning is recorded in a comment at the point of change so it is not
  reintroduced.

  2.3 Verification
  ----------------
      - Next.js reports zero errors, warnings or hydration mismatches in the
        production server log.
      - All 11 measured routes return HTTP 200 with real markup.
      - Arabic (/ar) renders 454 characters of real Arabic text, dir="rtl",
        with the Cairo webfont preloaded.
      - The product detail page returns the correct <title> and the product
        name appears in real markup rather than only in the RSC payload.
      - tsc --noEmit clean; npm run build exit 0.

================================================================================
  4. FRONTEND — OPTIMISATIONS APPLIED
================================================================================

  4.1 Removed the SSR null guard (CartContext.tsx)
  -----------------------------------------------
  The fix described in section 2. This is the change that matters.

  4.2 Server-side catalogue fetching with caching
  ------------------------------------------------
  New file: main-website/lib/server-api.ts

  Every storefront read went through lib/api.ts, an axios facade over
  @nod/shared. Next.js only caches its Data Cache for the NATIVE fetch; an
  axios request is an opaque outgoing HTTP call the framework knows nothing
  about, so it is never cached, never deduplicated and never revalidated.

  lib/server-api.ts uses native fetch with an explicit revalidate window and
  cache tags. Wired into:

      homepage      Stories, Hero products, Collections
      PDP           product detail (also removes a confirmed double fetch)

  Design constraints honoured:
      - never throws. Every function resolves to null on failure, so a dead
        API degrades to the existing skeleton rather than a 500.
      - only public, visitor-independent data is cached. Nothing derived from
        a cookie, cart or session passes through it.
      - every consumer keeps its own client fetch as a fallback, so first
        load is server-rendered while client-side navigation still shows the
        skeletons.

  Measured: 6 consecutive homepage requests produced 0 backend calls to
  /catalog/products/hero. TTFB fell from 54 ms to 28 ms as the cache warmed.

  Revalidation is 60s for catalogue, 120s for content. This is a real
  trade-off, not a free win: an admin product edit can take up to 60s to
  appear. The correct long-term fix is an on-demand revalidateTag call from
  the admin panel on save, not a shorter window.

  4.3 Eliminated the client-render bailout
  -----------------------------------------
  New file: main-website/app/useQueryString.ts

  PageTracker.js and BehaviorTracker.js called useSearchParams() to read the
  query string. That hook reads request-time state, so Next.js marks the
  entire route BAILOUT_TO_CLIENT_SIDE_RENDERING and ships an empty body with
  the data in a script payload for the client to render.

  Both components render null and use the value strictly inside effects, so
  the value is only ever needed in the browser, where window.location already
  holds it. They now use a new hook that:
      - reads window.location.search (initial value '' to avoid a hydration
        mismatch, since the server has no window);
      - stays reactive by patching history.pushState / replaceState to
        dispatch an event, because pushState deliberately fires none, and
        listening for popstate for back/forward;
      - installs the patch once per module and reference-counts it, so
        multiple consumers do not stack wrappers.

  app/shop/page.tsx legitimately needs its ?category= filter to seed state, so
  it received the documented Suspense boundary. That is also what made the
  masked /checkout build error visible.

  4.4 Web fonts
  -------------
      - Subset to the characters the site can actually display. The set was
        built from the Latin Unicode ranges plus every codepoint appearing in
        the source, and validated against live database content (product
        names, descriptions, stories): the database contributed ZERO codepoints
        the safe set did not already contain. Cairo additionally carries the
        Arabic block and presentation forms.
      - Re-encoded as WOFF2. 348 KB -> 52 KB, 345 KB -> 128 KB.
      - font-display: swap added to both faces. This was the actual defect:
        without it the browser holds back the first paint of any text using
        the family until the font arrives, which on a slow connection is up to
        a second of invisible text.
      - Content-hashed filenames. public/ is served with
        Cache-Control: public, max-age=0 by default, so the font was being
        revalidated on every single page view. Because the hash changes when
        the bytes do, a headers() rule in next.config.ts can safely serve them
        max-age=31536000, immutable. A stable filename could not be cached
        that hard without stranding a font fix for a year.
      - Preload: Rubic always (NavBar.css uses it on every page); Cairo only
        when dir is rtl, because on an English page preloading it would spend
        128 KB on a font that renders no glyph. crossOrigin="anonymous" is
        set, without which the browser fetches the font twice.
      - The 8 dead faces and their files were removed (1,387 KB).

  4.5 Images
  ----------
      - next/image with formats ['image/avif','image/webp'].
      - 13 of 17 <img> elements converted. The 4 that remain are deliberate:
        SVG flags (the optimiser blocks SVG by default) and explicit
        width/height where fill would collapse a container that has no
        intrinsic height.
      - remotePatterns derived from the environment rather than hardcoded, so
        the LAN dev address keeps working when it changes.
      - dangerouslyAllowLocalIP gated on NODE_ENV !== 'production'. Next 16
        blocks loopback and private ranges as SSRF hardening. That is correct
        in production, where media is on the public media host, and wrong in
        development, where media is the same machine.

  4.6 Dead dependencies
  ---------------------
  9 packages removed, 91 transitive packages eliminated. Each was verified to
  have zero imports repo-wide, including inside the vendored @nod/shared
  design system:

      @emotion/react, @emotion/styled, @mui/material, class-variance-authority,
      framer-motion, gl-matrix, lucide-react, mathjs, react-fast-marquee

  main-website now declares 9 direct dependencies:
      axios, clsx, next, react, react-confetti, react-dom, react-toastify,
      swiper, tailwind-merge

  4.7 Middleware renamed to proxy, and a locale bug fixed
  -------------------------------------------------------
  middleware.ts -> proxy.ts, exporting proxy(), per Next 16.2.2. This removed
  a deprecation warning and the asset matcher was extended to avif/mp4/webm.

  A real bug was fixed while doing it: the middleware WROTE the NEXT_LOCALE
  cookie but never READ it. An Arabic user following any unprefixed link was
  therefore redirected to /en. It now reads the cookie, seeds it on first
  visit, and validates it against LOCALES.includes() so a tampered value
  cannot inject an arbitrary locale.

================================================================================
  6. BACKEND — OPTIMISATIONS APPLIED
================================================================================

  6.1 Prisma connection pool raised to 40
  ---------------------------------------
  DATABASE_URL in the root .env now carries ?connection_limit=40.

  Prisma's default pool is num_cpus * 2 + 1, which is 9 on this 4-core box.
  Under a burst that serialises work behind 9 connections. Measured on a
  30-way burst of 0.4s queries:

      pool  9   1701 ms
      pool 40    449 ms          3.8x faster

  40 was chosen against max_connections=151, leaving ample headroom for the
  control plane, the outbox worker and administrative sessions. The rationale
  is recorded in backend/config/prismaClient.ts.

  Note: .env cannot carry comments. scripts/sync-env.mjs rewrites the entire
  file from parsed key/value pairs whenever SAFE_ORIGINS changes, and its
  parser discards comment lines. The rationale therefore lives in the source
  file, not the .env.

  6.2 Single long-lived Prisma client
  ------------------------------------
  backend/config/prismaClient.ts keeps one client on globalThis. Without it,
  dev-mode module reloads leak connection pools until the server hits
  max_connections and refuses all traffic.

  6.3 Rate limiting hardened
  --------------------------
  Four tiers, Redis-backed, IPv6-aware. See 5.5.

  6.4 Transactional outbox
  -------------------------
  backend/services/outbox.ts with workers/outboxWorker.ts and
  workers/outboxHandlers.ts implements a claim-lease, dead-letter and sweep
  state machine, so a side effect is never lost because a process died between
  committing the business transaction and publishing the event.

  6.5 Order creation and stock
  -----------------------------
  backend/services/orderService.ts performs order creation with retry, and
  exposes getPublicOrderDetails. Stock is decremented at placement and
  restored only on an admin transition to Cancelled or Refunded. Payment is
  Cash on Delivery.

  6.6 Regression suite
  --------------------
      npx vitest run --root backend
        3 files, 21 tests, all passing (1.11s)

      npm run check:radius
        5/5 nestings satisfy outer = inner + padding

================================================================================
  7. OPEN DEFECTS AND RISKS
================================================================================

  These are real and currently unfixed. They are listed rather than quietly
  omitted.

  7.1 273 KB gzipped of JavaScript is now the top frontend cost
  ------------------------------------------------------------
  Section 3.2. With the HTML finally carrying content, JS no longer blocks the
  first paint the way it did, but it still dominates total transfer and
  hydration time. The largest single chunk is 69 KB gzipped. This needs a
  deliberate pass to find what is in it; it was not attempted here.

  7.2 Direct-to-media URLs are baked with the loopback host
  --------------------------------------------------------
  Now that pages are server-rendered, media URLs are computed on the server
  and baked into the HTML. In this LAN configuration that host is
  localhost:5002, so images that bypass the optimiser — the Egypt flag SVG —
  will be requested from the visitor's own localhost and fail until hydration
  re-derives the address.

  Optimised images are unaffected: they are requested through /_next/image,
  which the SERVER resolves, so the browser never contacts the media host
  directly.

  Production is not affected. media.nodmakeup.com is not a loopback host, so
  deriveClientBaseUrl returns it verbatim on both the server and the client.

  Verification on a phone should specifically check the flag icon.

  7.3 Every route is dynamic; there is no static or ISR rendering
  -------------------------------------------------------------
  The root layout awaits cookies() to read the locale, which forces all 11
  routes to ƒ (Dynamic). Pages are server-rendered, so this is far better than
  before, but nothing is prerendered and no page is served from a static shell.

  The correct fix is a [locale] route segment with generateStaticParams, which
  makes the locale part of the route rather than a cookie read. That is a
  routing change touching the proxy and the redirect logic that has already
  been verified, so it is proposed rather than done.

  7.4 /catalog/categories requires ?public=true
  ----------------------------------------------
  Without the query parameter the endpoint returns 401. The storefront calls it
  correctly with the parameter and receives 200, so there is no live bug. This
  corrects an earlier claim in this engagement that the storefront's category
  list was silently empty; it is not.

  7.5 scripts/sync-env.mjs silently deletes comments in .env
  ----------------------------------------------------------
  Any time SAFE_ORIGINS changes, the file is rewritten from parsed key/value
  pairs and every comment line is lost. There is no warning.

  7.6 121 pre-existing orders are unowned
  ----------------------------------------
  They are no longer retrievable through the public endpoint.

  7.7 main-website never imports the vendored @nod/design-system
  --------------------------------------------------------------
  It has its own app/design-system/, so `materialize-shared . --design-system`
  is dead weight on every install.

  7.8 Observability gaps
  ----------------------
      slow_query_log is OFF, so slow queries cannot be identified from the
      database side. Redis queue depth could not be sampled during this
      analysis (the probe timed out) and remains unmeasured.

================================================================================
  8. RECOMMENDED NEXT STEPS, IN PRIORITY ORDER
================================================================================

   1. Reduce the 273 KB gzipped JS bundle.
      Now the largest remaining frontend cost. Start by identifying what is in
      the 69 KB gzipped chunk. Route-level dynamic import for the PDP, cart
      drawer and checkout would cut the homepage's share.

   2. Visual confirmation on localhost:3001, then on a phone.
      Specifically: content appears immediately with no blank flash; no layout
      shift; no broken images; flag icon renders; no sideways scroll;
      skeletons still appear on client-side navigation; Arabic renders with
      Cairo and correct RTL; add-to-cart, checkout and the variant selector
      all work.

   3. Mirror, commit and push to nodmakeuop-platform, then deploy to Vercel.
      Requires Root Directory = main-website plus the environment variables
      listed in vercel-env.txt. Note the risk: if NEXT_PUBLIC_MEDIA_URL is
      absent on Vercel, deriveClientBaseUrl falls back to window.location and
      images will not be optimised at all.

   4. Enable slow_query_log before making further database changes, so the
      next round of optimisation is measured rather than guessed.

   5. Consider on-demand revalidation (revalidateTag from the admin panel on
      product save) to replace the 60-second staleness window.

   6. Consider the [locale] route segment to make routes statically
      generated. Larger change; do it on its own, with its own review.

   7. Optional, previously deferred:
      - a releases_stock boolean on order_status
      - CI has no deploy or migration job
      - start.sh --stop <service> is a no-op against a stale PID file
      - trim node_modules from the vendored @nod/shared
